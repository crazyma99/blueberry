## 0-1 完整迁移执行方案

共 6 个阶段，完全适配 blueberry 现有的「多 Profile 模板化」工程体系，遵循「架构先通、公共层先迁、业务分批落地、灰度验证上线」原则。

### 阶段 1：基线冻结与资产盘点

**核心目标：冻结变更、盘点资产、明确目标，避免迁移过程中代码漂移。**

1. **分支与版本冻结**
   - 从主干 `main` 切出独立迁移分支 `feat/vue3-migration`，迁移期间主干仅修复线上 bug，新功能开发暂停
   - 记录当前线上版本的功能清单、性能指标、包体积数据，作为验收基准
2. **全量资产盘点**
   - 代码层：17 个页面、15 个自研组件、20 个 utils 工具模块、9 处`wx.`直调、16 处平台条件编译
   - 工程层：多 Profile 配置、7 个自动化脚本、产物校验规则、CI/CD 流程
   - 依赖层：所有 npm 依赖、第三方 SDK、埋点统计、合规能力
   - 交付物：《迁移资产盘点清单》《风险与工作量评估表》
3. **目标技术栈确认**
   - 框架：uni-app Vue3 最新稳定版
   - 语言：TypeScript 5.x（保持原项目的类型能力）
   - 构建：Vite 5 + `@dcloudio/vite-plugin-uni`
   - 样式：SCSS（与原项目一致）
   - UI 组件库：Wot UI v2 /uview-plus（二选一，建议 Day0 做 spike 验证）

### 阶段 2：工程底座迁移

**核心目标：先让工程体系跑通，再迁移业务代码，保留原项目的工程化能力。**

1. **两种落地路径选择**
   - **路径 A：全新初始化（推荐，对应 SPEC v2 思路）**：用官方模板从零搭建新工程，旧代码仅作行为对照逐页复刻。优点是无历史包袱、代码干净，适合需要长期维护的核心项目。
   - **路径 B：原地改造**：在现有仓库分支上直接替换依赖、转换文件格式。优点是保留 git 提交历史，适合中小型项目快速迁移。
2. **依赖与构建配置替换**
   - **package.json**
     - 移除 `@dcloudio/vite-plugin-uni-x` 等 uni-app x 专属依赖，替换为标准 uni-app Vue3 依赖
     - 脚本命名保持不变：`dev:mp-weixin` / `build:mp-weixin`，新增多端脚本（`dev:mp-toutiao`、`dev:mp-xhs`、`dev:h5` 等）
     - 保留所有 profile 相关的 npm 脚本入口
   - **vite.config.ts**
     - 插件替换：将 `@dcloudio/vite-plugin-uni-x` 替换为 `@dcloudio/vite-plugin-uni`
     - 路径别名：保留 `@/* → src/*` 配置，与原项目一致
     - 新增多端构建的条件配置，适配不同平台的编译参数
   - **tsconfig.json**
     - 替换为 uni-app Vue3 的标准类型声明，移除 UTS 相关类型定义
     - 保留原有的路径别名、编译选项配置
3. **核心配置文件迁移**
   - **manifest.json**
     - 保留基础字段：应用名称、描述、版本号、微信小程序 AppID
     - 移除 uni-app x 专属配置项，补充抖音、小红书等其他平台的配置节点
     - 权限声明、服务配置按各平台规范补充
   - **pages.json**
     - 页面路由、TabBar 配置、全局样式 90% 以上字段直接兼容
     - 移除 uni-app x 专属样式属性，新增各平台的条件编译配置（`condition` 节点）
     - 保留自定义 tabBar 的 `custom: true` 配置
4. **入口文件与目录结构适配**
   - 批量重命名：所有 `.uvue` 文件改为 `.vue`，所有 `.uts` 工具文件改为 `.ts`
   - 入口文件：`App.uvue` → `App.vue`，`main.uts` → `main.ts`
   - 完全保留原目录结构：`pages/`、`components/`、`utils/`、`static/` 层级不变

### 阶段 3：多项目 Profile 机制完整适配

这是 blueberry 项目的核心工程化能力，迁移后必须完整保留「一套模板，多项目复用」的能力，也是上一版回复截断的部分：

1. **核心机制完全保留**
   - `profiles/<project-key>/project.env` 管理私有配置的架构不变，不污染模板源码
   - 配置字段定义、字段含义、可选 / 必填规则全部保持对齐，降低业务方适配成本
2. **核心脚本改造（7 个脚本逐一适配）**
   - **`apply-profile.sh` / `lib/apply-profile.mjs`**
     - 替换目标文件后缀：从 `.uts`/`.uvue` 对应改为 `.ts`/`.vue`
     - 替换规则不变：依然是正则匹配注入，`MP_WEIXIN_APPID`、`API_BASE_URL` 等字段写入位置对应更新
     - 自动注入政策页面路由的逻辑，从 `pages.json` 的 UTS 格式适配为标准格式
   - **`sync-template.sh`**
     - 同步覆盖范围对应调整：`src/App.vue`、`src/main.ts`、`src/pages/`、`src/utils/` 等
     - 保留规则不变：`package.json`、`profiles/`、`src/static/` 等项目私有内容不会被覆盖
   - **`build-miniapp.sh`**
     - 构建命令从 uni-app x 编译器改为标准 uni-app 构建命令
     - 新增多平台参数支持，可指定构建微信 / 抖音 / 小红书等不同端
     - 保留「同步模板 → 应用 Profile → 安装依赖 → 编译 → 产物校验」的完整流水线
   - **`verify-miniapp.sh`**
     - 校验目标文件路径更新：从 `utils/http.uts` 改为 `utils/http.ts`
     - 保留全部校验项：AppID 一致性、导航栏标题、本地协议页面、`X-App-Code` 请求头、残留字符串扫描
     - 新增多平台校验能力，可针对不同平台产物执行校验
   - **`new-miniapp-project.sh` / `create-profile.sh`**
     - 内置模板从 uni-app x 版本更新为 Vue3 版本
     - 初始化流程、git 初始化、依赖安装逻辑保持不变
   - **`release-miniapp.sh`**
     - 产物输出路径适配，发布流程与导入提示保持一致
3. **静态资源与配置映射不变**
   - `profiles/<key>/static/*` 复制到 `src/static/` 的逻辑完全保留
   - 所有字段的写入位置映射关系保持一一对应，仅调整文件后缀

### 阶段 4：代码层分层迁移

**核心原则：业务层禁止直调平台 API，禁止硬编码样式，所有平台差异收敛到适配层。**

1. **工具层（utils）优先迁移**
   - `config.uts` → `config.ts`：`API_BASE_URL` 环境变量注入逻辑适配
   - `http.uts` → `http.ts`：统一请求封装、自动附加 `Authorization` / `X-App-Code`、401 自动登出逻辑完整迁移
   - `auth.uts` → `auth.ts`：token 管理、用户信息、登录态、登录 / 登出流程迁移
   - `api.uts` → `api.ts`：26 个后端接口封装整体迁移，请求方法替换为标准 `uni.request`
   - `legal.uts` → `legal.ts`：协议名称、跳转函数迁移
2. **组件层迁移**
   - 基础组件替换：优先用成熟 UI 组件库替换自研基础组件（输入框、弹窗、选择器等），降低长期维护成本
   - 业务组件迁移：AppFooter、PhotoGrid、CustomTabBar 等 15 个业务组件逐行迁移，UTS 语法转 TS
   - 禁止组件内发请求、禁止组件内做平台判断
3. **页面层逐页迁移**
   - 迁移顺序：首页 → 相册列表 / 详情 → 价目表 → 我的 → 收藏 → 品牌馆 → AI 相关页面 → 政策页 / WebView
   - 模板语法适配：UTS 专属指令替换为标准 Vue3 指令，事件绑定、数据绑定语法对齐
   - 样式适配：补齐 uni-app x 不支持的 CSS 属性，rpx 单位保留
4. **平台适配层建设（多端核心）**
   - 新建 `src/common/platform/` 目录，定义统一的 `PlatformAdapter` 接口
   - 分平台实现：`WeixinAdapter.ts`、`TtAdapter.ts`、`XhsAdapter.ts`
   - 所有 `wx.` 直调、平台条件编译**只允许出现在适配层**，业务层统一调用 `getPlatformAdapter()`
   - 平台差异能力按降级策略处理：比如抖音无企业微信客服，则降级为拨号 + 提示

### 阶段 5：多平台扩展与适配

1. 新增抖音、小红书、H5 等平台的构建命令与产物目录
2. 补充各平台的 manifest 配置、权限声明、服务类目配置
3. 梳理平台能力差异矩阵，对不支持的能力做降级处理
4. 后端新增对应平台的域名白名单、登录 code2session 适配

### 阶段 6：验证、测试与上线

1. **构建验证**：三端（微信 / 抖音 / 小红书）构建全通过，`vue-tsc` 零错误
2. **功能验收**：17 个页面逐项对齐、核心业务链路全量回归
3. **产物校验**：运行 `verify-miniapp.sh`，确保 AppID、配置、无残留字符串
4. **真机测试**：微信 + 抖音双端 iOS/Android 真机冒烟测试
5. **灰度上线**：旧版本保持不变，新版本先小范围灰度，验证稳定后全量替换

## 三、行业同类重构的最佳实践流程

1. **双线并行，可回滚**：旧版本稳定维护，新版本独立分支开发，上线前随时可放弃，回滚成本为零
2. **骨架优先，业务后行**：先跑通工程底座、路由、基础框架、适配层，再逐页填充业务代码
3. **差异收敛，业务纯净**：所有平台判断、平台 API 调用全部收敛到适配层，业务代码零平台耦合
4. **渐进式迁移，分批验证**：按页面 / 模块优先级分批迁移，完成一块验证一块，而非一次性全量替换
5. **自动化校验兜底**：构建产物自动校验配置、AppID、残留字符串，防止人工失误导致的线上事故
6. **组件库借力，减少自研**：优先选择生态成熟、多端兼容的组件库，把精力集中在业务逻辑上
7. **配置驱动，多端复用**：通过 Profile 配置机制实现一套代码多项目复用，而非复制多份代码

## 四、blueberry 项目专项优化建议

结合仓库现有的工程化能力，迁移时可以同步做以下提升：

1. **强化校验脚本**：新增多平台专属校验规则、平台残留代码扫描，进一步降低串号风险
2. **构建流水线优化**：新增多平台并行构建能力，统一发布流程
3. **设计 token 体系化**：借迁移机会落地完整的 design token，样式统一管理，禁止硬编码
4. **保留提交历史**：建议使用原地分支迁移，而非全新仓库，保留代码历史追溯能力
